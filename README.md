# Booking Service

Задание:
> Нужно реализовать небольшой backend-сервис для записи на встречи. Пользователь создаёт бронь через REST API, система ставит её в очередь, воркер асинхронно подтверждает запись и логирует mock-уведомление. Фронтенд не нужен — только API, воркер и тесты.

## Стек

- **FastAPI** — асинхронный REST API
- **SQLAlchemy 2.0 (async)** + **asyncpg** — ORM и драйвер PostgreSQL
- **Alembic** — миграции БД
- **Celery** + **Redis** — воркер и очередь задач
- **Pydantic v2 / pydantic-settings** — валидация и конфигурация
- **uv** — пакетный менеджер
- **Ruff** — линтер и форматтер
- **pytest** + **pytest-asyncio** — тесты

## Запуск

Для запуска нужны docker и docker-compose.

1. Создайте `.env` в корне проекта (пример — `.env.example`):

   ```env
    PROJECT_NAME = Booking Service
    API_PREFIX = /api

    # DATABASE CONFIG
    DB_HOST = db
    DB_PORT = 5432
    POSTGRES_USER = postgres
    POSTGRES_PASSWORD = postgres
    POSTGRES_DB = booking_service

    # REDIS CONFIG
    REDIS_HOST = redis
    REDIS_PORT = 6379
    REDIS_PASSWORD = redis_password
   ```

   Хосты `DATABASE_HOST` и `REDIS_HOST` задаются в соответствии с названием сервисов в `docker-compose.yml`
   (`db` и `redis`).

2. Запустите проект:

    Для удобства настроен Makefile. Все доступные команды можно увидеть с помощью команды:
    ```bash
    sudo make help
    ```
    ---
    Запуск проекта может осуществляться с помощью одной из двух команд:
    ```bash
    sudo make build
    ```
    для запуска контейнеров без отображения логов

    ```bash
    sudo make dev
    ```
    для запуска контейнеров с логами в консоли

    ---
   При старте поднимается следующая цепочка:
   - `db` (PostgreSQL) и `redis` ждут готовности по healthcheck;
   - одноразовый сервис `migrate` применяет миграции (`alembic upgrade head`);
   - после успешной миграции стартуют `api` и `worker`.

3. API доступен на `http://localhost:8000/api`, интерактивная документация —
   `http://localhost:8000/api/docs`.

### Пример запроса

```bash
curl -X POST http://localhost:8000/api/bookings \
  -H "Content-Type: application/json" \
  -d '{
        "name": "Иван",
        "booking_datetime": "2026-06-20T14:00:00+03:00",
        "service_type": "consultation"
      }'
```

В ответ возвращается созданная бронь со статусом `pending`. Через несколько
секунд воркер переведёт её в `confirmed` (или в `failed`). Проверить
статус:

```bash
curl http://localhost:8000/api/bookings/1
```

`service_type` принимает значения из перечисления `ServiceType` (подробнее смотрите в документации к api); недопустимое
значение отклоняется с кодом `422`.

## Тесты

> необходимо установить пакетный менеджер uv 
> ```bash
> curl -LsSf https://astral.sh/uv/install.sh | sh
> ```

Тесты не требуют Docker и запускаются из корня проекта. Внешние зависимости
подменяются: вместо PostgreSQL — SQLite в памяти, вместо брокера — заглушка.

```bash
sudo make install       # необходимо наличие пакетного менеджера uv
sudo make test          # или make test
```

Покрытие:
- **API** — happy path (создание и чтение брони) и граничные кейсы
  (404 на несуществующей брони, 422 на невалидном `service_type` и неполном теле);
- **Воркер** — успех (статус → `confirmed`), имитация сбоя внешнего сервиса
  (исключение под retry) и идемпотентность (повтор по уже подтверждённой брони
  не меняет статус). Случайность сбоя детерминируется через `monkeypatch`.

## Технические решения

### Выбор фреймворка

**FastAPI** выбран как async-нативный фреймворк: вся цепочка (API → БД → воркер)
работает на одном асинхронном стеке без блокировки event loop. Дополнительно он
даёт валидацию запросов и ответов через Pydantic и автоматическую
OpenAPI-документацию из коробки.

Был выбран из-за того, что проект представляет из себя API-only сервис, а альтернатива в виде Django добавит лишнюю админ-панель, также Django является синхронным, что может останавливать выполнение программы при недостаточном количестве волкеров... Ну и я хотел продемонстрировать своё умение в архитектуру :)

**Celery + Redis** — для очереди и воркера. Async-нативный **TaskIQ** рассматривался как альтернатива (он убирает
необходимость в `asyncio.run` внутри задач и связанные с этим нюансы event loop),
но для данного задания предпочтение отдано более распространённому Celery.

### Архитектура

Слоистая структура с явным разделением ответственности:

```
роутер → сервис → репозиторий → БД
```

- **роутер** — только HTTP: разбор запроса, вызов сервиса, формирование ответа;
- **сервис** — бизнес-логика (создать бронь и поставить задачу в очередь);
- **репозиторий** — доступ к данным (CRUD), не знает ни про HTTP, ни про очередь.

Такое разделение упрощает тестирование: каждый слой проверяется изолированно, а
репозиторий и сервис не зависят от веб-слоя.

Ошибки доменного уровня (`BookingError`, `BookingNotFoundError`) кидаются в
репозитории/сервисе и превращаются в HTTP-коды (400 / 404) централизованно через
обработчики исключений FastAPI — слой данных остаётся HTTP-агностичным.

Можно было написать исключения для всех возможных ошибок, но для такого небольшого проекта - это too much.

### Структура задачи воркера

Воркер получает `booking_id` сразу после создания брони. Задача:

1. С вероятностью ~15% имитирует сбой внешнего сервиса уведомлений (кидает
   исключение).
2. При успехе переводит бронь в `confirmed` и логирует mock-отправку уведомления.
3. Упавшие задачи ретраятся с **экспоненциальным backoff**
   (`autoretry_for` + `retry_backoff`).
4. После исчерпания ретраев статус брони становится `failed`.

### Идемпотентность

Повторный запуск задачи с тем же `booking_id` не создаёт дубль и не ломает
статус. Это обеспечивается двумя свойствами:

- задача **только обновляет статус существующей** брони,
  поэтому дубликаты невозможны;
- перед обработкой проверяется текущий статус: если бронь уже `confirmed`, задача
  завершается без изменений. Это защищает от ситуации, когда повторный запуск переопределит уже подтверждённую запись на `failed`.

### Дополнительно

- **Structured logging** — логи в формате JSON (поля `ts`, `level`, `logger`,
  `message` + произвольные поля через `extra`), удобно для парсинга.
- **Rate limiting** — ограничение на `POST /bookings` через slowapi с хранилищем
  в Redis (работает корректно при нескольких репликах API).
- **Makefile** — команды `dev`, `test`, `lint`, `migrate`, `up`, `down`, `build`.

## Структура проекта

```
booking_service/
  api/
    routers/        # HTTP-эндпоинты
    schemas/        # Pydantic-схемы запросов/ответов
  logic/            # сервисный слой (бизнес-логика)
  repositories/     # доступ к данным
  db/               # модели SQLAlchemy, сессия, движок
  worker/           # Celery: инстанс и задачи
  config/           # настройки (pydantic-settings)
  exceptions/       # доменные исключения
  main.py           # сборка приложения FastAPI
alembic/            # миграции
tests/              # pytest
dockerfiles/        # все Dockerfile хранятся здесь
docker-compose.yml
Makefile
pyproject.toml
uv.sync
```
